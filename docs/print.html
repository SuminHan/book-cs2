Why Programming Matters

원본 슬라이드: why-programming-matters.pdf

“이제 AI가 코드를 짜준다. 나보다 빠르고, 솔직히 나보다 더 잘 짠다. 그런데 내가 왜 프로그래밍 수업에 앉아 있어야 하지?”

정당한 질문이다. 그리고 “AI는 코딩을 잘 못한다“는 식으로 답할 생각은 없다. 못하지 않는다. 아주 잘하고, 매달 더 좋아지고 있다. 대신 다른 방식으로 답하려 한다 — 그래서 어떤 일이 새로 생겼는지 보여주는 방식으로.

What Changed

이진 탐색을 짜달라고 하면 즉시 나온다. 그리고 맞다. 10년 전엔 한 주치 수업 분량이었다. 지금은 4초. 그럼 무엇이 비싸졌는가?

병목이 옮겨갔다.

예전지금
어려운 부분코드를 쓰는 것코드를 판단하는 것
하루 100줄을 썼고, 그 100줄을 전부 이해하고 있었음 — 쓰려면 이해할 수밖에 없으니까1분이면 1000줄을 뽑음. 그중 몇 줄이나 이해하고 있나?

AI가 좋아진다고 이 일이 줄지 않는다. 오히려 늘어난다.

이건 이미 취업 시장에서 나타나고 있다: 신입과 인턴은 취업하기 더 어려워졌고, 빅테크의 평균 연차는 계속 올라가는 중이다 — 그런데 동시에 상위 테크 기업 채용은 1년 전보다 약 20% 증가했고, AI 엔지니어링 공고는 Apple, Google 등에서 50~100% 증가했다.1 둘 다 동시에 참이다. 왜? 예전에 입문하는 방법은 “작고 명확하게 정의된 과제를 줄 테니 구현해와라“였다. 그건 지금 AI가 가장 잘하는 일이다. 그 첫 계단이 사라졌다. 남은 일은 한 단계 위에서 시작한다 — 결정하고, 지시하고, 검증하는 일.

들어갈 때는 한국어든 영어든 사람의 언어를 쓸 수 있다. 하지만 돌아올 때는 답이 항상 코드다 — 출력에는 한국어 버전이 없다. 오직 코드가 있을 뿐이고, 그걸 읽을 수 있느냐만 남는다. 돌아온 것을 읽지 못한다면, 지시를 한 게 아니라 소원을 빈 것이다.

The Gap

“성적 계산기를 만들어줘“라고 시켜봤다. 이렇게 나왔다 — 깔끔하고, 읽기 쉽고, 잘 돌아간다:

def final_grade(scores, attendance_rate):
    average = sum(scores) / len(scores)
    if attendance_rate < 0.75:
        return "Fail"
    return "Pass" if average >= 70 else "Fail"

맞아 보인다. 돌아간다. 에러도 없다. 그런데 이 수업 기준으로는 틀렸다.

중요한 건 이 부분이다: 어디를 봐도 틀려 보이지 않는다는 것. 경고해주지 않는다. 그냥 조용히 잘못된 성적을 계산할 뿐이다.

세 가지를 알 수 없었다:

  • 어떤 학생이 병결로 시험을 못 봤다. 우리 규정은 인정점수에 80% 가중치를 — 공결이면 100%를 적용한다. 코드에는 둘 다 없다.
  • 어떤 학생이 Fail을 받고 재시험을 봤다. 어느 점수를 쓰는가? 코드는 재시험이란 걸 들어본 적이 없다.
  • 출석 3/4 미만 — 이게 모든 걸 덮어쓰는가, 아니면 먼저 확인하는가? 코드는 찍었다. 그리고 우리와 다르게 찍었다.

“그럼 규정을 프롬프트에 넣으면 되잖아요!” — 맞다. 그런데 그렇게 하려면 뭐가 빠졌는지를 이미 알아챘어야 한다. 코드는 알려주지 않았다. 구멍을 보려면 읽는 수밖에 없었다.

The Trap

과제: 어떤 연도가 윤년이면 True를 반환.

def is_leap_year(year):
    if year % 4 == 0:
        return True
    else:
        return False

테스트해봤다: is_leap_year(2024) → True, 정답! 통과했다. 이대로 제출?

is_leap_year(1900)을 테스트해보면 — 기대값은 False(1900년은 윤년이 아니었다)인데 실행 결과는 True. 왜: 진짜 규칙은 세 부분이다 — 4로 나누어떨어지고, 단 100으로 나누어떨어지면 제외하되, 그중 400으로 나누어떨어지면 다시 윤년. 코드는 첫 부분만 알고 있다. 1900은 100으로는 나뉘지만 400으로는 안 나뉘므로 윤년이 아니다.

버그는 처음부터 거기 있었다. 테스트가 그쪽을 안 봤을 뿐이다. 테스트를 통과했다는 건 맞다는 뜻이 아니다. 어떤 입력이 이걸 깨뜨리는지 고르는 것 — 그게 실력이다. 그리고 그건 아무도 대신 해줄 수 없다.

같은 패턴이 실제로도 있었다: NASA의 Mars Climate Orbiter는 10개월을 날아갔고, 화성 상공 약 150km에 안착할 예정이었으나 실제로는 57km로 진입해 대기권 한복판에서 부서졌다 — 한 팀은 추력 값을 파운드힘(lbf) 단위로 넘겼고, 받는 팀은 그걸 뉴턴(N)으로 읽었다. 1 lbf = 4.45 N이라 모든 궤도 수정이 4.45배씩 어긋난 채로 10개월이 지났다. 손실 1억 2500만 달러. 그 코드는 한 줄도 빠짐없이 완벽하게 돌아갔다. 그 숫자가 무슨 뜻인지 아무도 확인하지 않았을 뿐이다.

Your Job

1950년 튜링은 “기계가 생각할 수 있는가?“라고 물었고 — 답하기를 거부했다. 대신 시험으로 바꿨다: 사람 심판이 양쪽에 질문을 던지고 그 답이 말이 되는지 판단한다. 컴퓨터의 맨 처음 설계에 이미 질문을 던지는 사람이 의자에 앉아 있었다. 그 의자는 끝내 자동화되지 않았다.

이 과목의 교과 핵심역량 네 가지 — 그리고 방금 각각을 어디서 만났는지:

  • Fundamental Programming & Problem-Solving — 돌아온 코드를 읽고, 그게 실제로 무슨 일을 하는지 이해하기
  • Logical Thinking & Analytical Skills — 어떤 입력이 이걸 깨뜨릴지, 깨지기 전에 알기
  • Communication & Collaboration — 수업 시간에 문제를 같이, 소리 내어 푸는 이유
  • Ethical Use of AI & Responsible Attitude — 도구는 쓰되, 답에 대한 책임은 내가 진다. “AI가 짰는데요“는 변명이 되지 않는다.

기계보다 코드를 빨리 치려고 여기 온 게 아니다. 원하는 것을 정확히 말할 수 있고, 돌아온 것을 읽을 수 있고, 어떤 입력이 깨뜨릴지 아는 사람이 되기 위해서다. 그래서 수업은 이렇게 운영된다: 수업 시간에 문제는 AI 없이, 다 같이, 손으로 푸는 게 원칙이다. AI를 쓰는 게 부정행위라서가 아니라 — 기계가 대신 해주는 능력은 내 것이 되지 않기 때문이다.

평생 계산기를 쓸 것이다. 그래도 산수는 손으로 배웠다.

왜 복습부터인가

Lists / Strings

📓 Jupyter Notebook 열기

“서버가 요청받은 길이만큼, 확인도 없이 메모리를 그대로 잘라 돌려준다면?”

2014년 4월, 암호화 라이브러리 OpenSSL에서 하트블리드(Heartbleed)라는 취약점이 발견됐다. 원인은 단순했다: 서버는 클라이언트가 “이만큼의 데이터를 돌려달라“고 요청하면, 실제로 받은 데이터의 길이는 확인하지 않고 요청한 길이만큼 그대로 메모리에서 잘라 돌려줬다. 클라이언트가 “나는 1바이트를 보냈지만, 6만 4천 바이트를 돌려달라“고 요청하면, 서버는 그 1바이트 뒤에 있는 — 전혀 상관없는 — 메모리 6만 4천 바이트를 그대로 잘라서 돌려줬다. 거기엔 다른 사용자의 비밀번호나 서버의 개인키가 들어 있을 수도 있었다.

L[i:j]가 실제로 하는 일

이번 주 배우는 slicing 연산자 L[i:j]는 “리스트의 실제 길이“와 무관하게 인덱스 i부터 j-1까지를 잘라낸다. L이 정말 그 길이를 갖고 있는지는 프로그래머가 확인해야 하는 몫이다. Python은 리스트 경계를 넘어가면 에러를 내주지만, 하트블리드가 발생한 C 언어의 메모리 조작에는 그런 보호장치가 없었다. “요청한 길이“와 “실제 있는 길이“를 혼동하면, 있어서는 안 될 데이터까지 함께 잘려 나온다.

오늘 배우는 것과의 연결

전 세계 웹 서버의 상당수가 이 취약점에 노출되어 있었고, 복구에는 수개월이 걸렸다.1 len(·)으로 실제 길이를 확인하고 그 범위 안에서만 인덱싱/슬라이싱하는 습관은 사소해 보이지만, 이 사고가 벌어진 근본 원인과 정확히 같은 지점을 다룬다.

어떤 인덱스가 유효한지 항상 정확히 알고 있을 것 — 이번 주 배우는 List/String 연산은 모두 그 위에 세워진다.

Loops

📓 Jupyter Notebook 열기

2016년, 국제탐사보도언론인협회(ICIJ)는 파나마의 로펌 모색 폰세카에서 유출된 문서 1,150만 건, 총 2.6테라바이트를 넘겨받았다. 사람이 한 장씩 읽는다면 평생이 걸릴 분량이었다.

기자 수백 명이 협업한 끝에 한 일은, 결국 문서 하나하나를 훑으며 같은 질문을 반복해서 던지는 것이었다 — 특정 이름이 등장하는 문서가 있는가 (for some), 조건을 만족하는 문서가 몇 건인가(counter). 이번 주에 배우는 패턴 그대로다.

for 루프가 실제로 하는 일

words = open("input.txt", "r").read().split()

count = 0
for w in words:
    if w == "Gunnlaugsson":
        count += 1

for w in words:가 하는 일은 정확히 이거다 — words의 원소를 앞에서 부터 순서대로 하나씩 w에 꺼내 담고, 그때마다 몸통(if w == "Gunnlaugsson": count += 1)을 한 번씩 실행한다. words의 길이가 5든 1,150만이든 코드는 단 한 글자도 바뀌지 않는다 — 몸통이 실행되는 횟수만 다를 뿐이다. 사람이 눈으로 1,150만 건을 읽을 수는 없어도, 컴퓨터는 이 루프 하나로 초당 수만 건을 검사할 수 있다.

(참고: .split()은 공백 기준으로 쪼개므로 words의 원소는 "Mossack", "Fonseca"처럼 한 단어씩이다 — 그래서 두 단어로 된 이름을 통째로 비교하려 하면(w == "Mossack Fonseca") words 안에 그 형태 그대로인 원소가 없어서 절대 True가 되지 않는다. 위 코드가 성(姓) 하나만, "Gunnlaugsson"으로 비교하는 이유다.)

오늘 배우는 것과의 연결

"Gunnlaugsson"은 실제로 유출 문서에 등장했던 이름이다 — 아이슬란드 총리 시그뮌뒤르 귄로이그손의 아내 명의로 등록된 역외회사 Wintris가 문서에서 발견됐고, 은행 채권자와의 협상 당사자였던 총리가 그 회사를 신고하지 않은 사실이 드러나면서 대규모 시위 끝에 그는 2016년 4월 사임했다.1 시작은 별다를 것 없는 “파일 열기 → 한 줄씩 훑기 → 이름 확인하기“였는데, 그 결과가 총리 사임이었다.

오늘 배우는 for all / counter / max-min 패턴은 데이터가 5줄이든 1,150만 건이든 똑같이 적용된다 — 다른 건 오직 컴퓨터가 대신 훑어준다는 사실뿐이다.

Multi-Dimensional Lists

📓 Jupyter Notebook 열기

2010년, 경제학자 카르멘 라인하트와 케네스 로고프는 “정부 부채가 GDP의 90%를 넘으면 경제성장률이 급격히 떨어진다“는 연구 결과를 발표했다. 이 논문은 2008년 금융위기 이후 유럽과 미국의 긴축 재정 정책을 정당화하는 핵심 근거로 반복 인용됐다.

2013년, 대학원생 토머스 헌든이 이 논문의 계산을 재현하려다 원본 엑셀 파일을 입수했다. 원인은 범위 선택 실수였다: 20개국의 평균 성장률을 구하는 수식이 실제로는 그중 5개국(호주, 오스트리아, 벨기에, 캐나다, 덴마크)이 들어있는 행을 계산 범위에서 빠뜨리고 있었다. 표 (2차원 데이터)에서 몇 개 행을 빼먹은 것 — 그것이 원인의 전부였다.

table[i]가 가리키는 것

2차원 리스트 table에서 table[i]는 정확히 “몇 번째 행“인지가 전부다. for i in range(height)로 도는 루프가 실제로 표의 모든 행을 포함하는지는 코드를 쓰는 사람이 직접 확인해야 한다 — 엑셀 수식이든 Python의 for 루프든, “몇 번째 줄부터 몇 번째 줄까지“를 정확히 지정하지 않으면 그만큼의 데이터가 조용히 빠진다.

오늘 배우는 것과의 연결

빠진 5개국을 포함시키자 논문의 결론은 뒤집혔고, “90% 부채 한도“라는 정책적 근거는 크게 흔들렸다.1

Pile of Cubes

📓 Jupyter Notebook 열기

몸 안을 째지 않고 들여다보려면 어떻게 해야 할까? 1970년대, 고드프리 하운스필드는 이 질문에 답을 내놨다 — 몸의 여러 각도에서 X선 사진을 찍고, 그 여러 장의 2차원 사진들로부터 몸속의 3차원 구조를 역으로 계산해내는 것. 이것이 CT(컴퓨터 단층촬영)의 원리이고, 하운스필드는 이 업적으로 1979년 노벨 생리의학상을 받았다.1

이번 주 다루는 “Pile of Cubes” 문제는 이 아이디어를 아주 단순화한 버전이다: 큐브 더미를 위/앞/오른쪽, 딱 세 방향에서 본 그림자(2차원 투영)만 가지고, 원래 3차원 구조를 역으로 알아낸다.

왜 유일하지 않은가

CT 스캐너가 수백 장의 각도에서 사진을 찍는 이유가 여기 있다 — 투영이 적을수록 같은 그림자를 만드는 3차원 구조가 여러 개 있을 수 있다. 이번 문제도 마찬가지다: 세 방향의 투영만으로는 원래 큐브 더미를 유일하게 복원할 수 없는 경우가 있다. 그래서 문제는 “정확히 복원하라” 대신 “그 투영을 만들 수 있는 것 중 큐브 개수가 최대인 것을 찾아라“로 바뀐다.

오늘 배우는 것과의 연결

세 방향의 그림자만으로 가장 그럴듯한 3차원 구조를 논리적으로 구성해 내는 방식은, 의료 영상부터 이번 주 3중 for 루프 코드까지 똑같이 적용된다.

세 장의 그림자에서 입체를 복원하는 이번 주 퍼즐은, 그 자체로 노벨상을 받은 아이디어의 축소판이다.

Gaussian Elimination

📓 Jupyter Notebook 열기

스마트폰이 “내 위치“를 알아내는 원리는 뜻밖에도 이번 주 배우는 내용과 맞닿아 있다. GPS 위성은 각자 자신의 위치와 신호를 보낸 시각을 계속 방송한다. 스마트폰은 최소 4개의 위성으로부터 신호가 도착하는 데 걸린 시간을 재서 위성까지의 거리를 계산하고, “내 위치에서 각 위성까지의 거리가 이만큼이다“라는 식을 위성 개수만큼 세워 풀어서 자신의 위치를 알아낸다 — 정리하면 미지수(위치 좌표와 시계 오차)에 대한 연립일차 방정식이 나온다.

\(n^3\)의 의미

행렬식(determinant)으로 직접 풀면 계산량이 \(n!\)에 비례해서 순식간에 감당할 수 없는 크기가 된다. Gaussian elimination은 같은 문제를 \(n^3\)에 비례하는 시간에 푼다 — 미지수가 몇 개뿐인 위치 계산이라면 초당 수십 번씩 반복해도 전혀 무리가 없는 속도다.

오늘 배우는 것과의 연결

이 방법 자체는 가우스(Gauss, 19세기 초)보다 훨씬 오래됐다 — 고대 중국 수학서 《구장산술(九章算術)》에 이미 사실상 같은 절차가 등장한다. 1 이름은 가우스를 따랐지만, “연립방정식을 체계적으로 소거해서 푼다“는 아이디어 자체는 2천 년 넘게 쓰여온 셈이다.

오늘 짜는 forward elimination 코드는, 2천 년 전 계산 기법과 스마트폰 GPS 칩이 지금도 똑같이 쓰고 있는 바로 그 절차다.

Spring Equilibrium (optional)

건물이나 다리를 설계할 때, 엔지니어는 실제로 짓기 전에 컴퓨터 안에서 먼저 무너뜨려본다. 구조물을 아주 작은 조각(요소, element)들로 잘게 나누고, 그 조각들이 스프링처럼 서로 힘을 주고받는다고 가정한 뒤, 모든 조각이 힘의 평형을 이루는 상태를 계산한다 — 이것이 유한요소해석 (Finite Element Analysis, FEA)이고, 오늘날 거의 모든 건물·다리·항공기· 자동차가 이 방식으로 설계·검증된다.

이번 주 문제가 실제로 하는 일

이번 주 다루는 문제는 이 아이디어를 그대로 축소한 것이다 — 자유롭게 움직이는 물체들이 스프링으로 연결되어 있을 때, 모든 물체가 동시에 힘의 평형을 이루는 위치를 구한다. 스프링의 원래 길이를 0으로 단순화하면, 이 평형 조건이 정확히 6주차에 배운 연립일차방정식이 된다 — 그래서 Gaussian elimination을 그대로 다시 쓸 수 있다.

오늘 배우는 것과의 연결

실제 유한요소해석은 요소가 수백만 개에 이르고, 스프링 하나보다 훨씬 복잡한 재료 모델을 쓴다. 하지만 “각 지점이 이웃과 주고받는 힘의 합이 0이 되는 위치를 찾는다“는 핵심 아이디어는, 이번 주 몇 개의 물체와 스프링으로 이루어진 작은 시스템과 다르지 않다.

작은 스프링 시스템의 평형을 계산하는 이번 주 코드는, 초고층 빌딩과 항공기를 설계하는 소프트웨어와 같은 자리에 서 있다.

Classes & Objects

1985년부터 1987년 사이, 방사선 치료기 Therac-25가 적어도 6건의 심각한 방사선 과다 노출 사고를 일으켰고, 그중 일부 환자는 목숨을 잃었다. 1 원인은 하드웨어 결함이 아니라 소프트웨어였다 — 여러 화면 (모드)이 같은 전역 변수들을 공유하며 상태를 주고받았는데, 특정 순서로 빠르게 키를 입력하면 한 화면이 남긴 상태값을 다른 화면이 미처 정리하지 못한 채로 읽어버리는 경우가 있었다.

이전 모델은 이런 소프트웨어 오류가 나더라도 하드웨어 안전장치가 최종적으로 막아줬다. Therac-25는 비용 절감을 위해 그 하드웨어 안전장치를 없애고 “소프트웨어가 알아서 안전을 보장할 것“이라고 가정했다. 문제는 그 소프트웨어의 상태가 여러 곳에 흩어진 전역 변수로 관리되고 있어서, 정확히 누가 언제 그 값을 바꾸는지 아무도 장담할 수 없었다는 데 있었다.

상태를 한곳에 가두기

이번 주 배우는 class는 정확히 이 문제를 겨냥한다: 관련된 상태 변수 (state 변수)들을 하나의 object 안에 가두고, 그 상태를 건드리는 함수도 그 object에 딸린 메소드로만 제한한다. self.x처럼 상태가 어디에 속하는지 항상 명시적이고, 상태를 바꾸는 쪽(modifier)과 읽기만 하는 쪽 (pure function)을 구분해서 부르는 습관도 여기서 나온다.

오늘 배우는 것과의 연결

class 하나로 이런 사고가 전부 방지되는 것은 아니다. 하지만 “이 데이터는 정확히 누가, 어떤 함수를 통해서만 바꿀 수 있는가“를 코드 구조로 분명히 하는 습관은, Therac-25 사고 이후 소프트웨어 공학 교육에서 빠짐없이 강조하는 원칙이 됐다.

상태를 아무 데서나 건드릴 수 있게 흩어놓지 않는 것 — 오늘 배우는 class의 가장 근본적인 이유다.

Stable Matching I

📓 Jupyter Notebook 열기

1900년대 초, 미국의 병원들은 의대생을 레지던트로 뽑을 때 서로 경쟁하듯 점점 더 이른 시점에 채용을 제안했다. 1940년대 말에는 학생이 아직 학교를 2년이나 더 다녀야 하는 시점에 이미 제안을 받는 일까지 벌어졌다 — 학생도 병원도 상대를 제대로 알지 못한 채 성급하게 결정을 내려야 했고, 나중에 더 나은 제안이 오면 이미 한 약속을 깨는 일도 잦았다.

이 혼란을 해결하기 위해 1952년, 미국의 병원과 의대생을 짝짓는 중앙 매칭 시스템(NRMP)이 도입됐다. 흥미로운 건 이 시스템이 쓰던 알고리즘이, 10년 뒤인 1962년 수학자 데이비드 게일과 로이드 섀플리가 발표한 이론 — 오늘 배우는 stable matching — 과 사실상 동일한 방식이었다는 점이다. 현장에서 먼저 문제를 실용적으로 풀어냈고, 이론이 나중에 그것을 수학적으로 설명해낸 셈이다.

Stable Matching이 막는 것

배정된 짝이 있는데도, 서로가 서로를 지금 짝보다 더 선호하는 다른 쌍(unstable pair)이 남아있다면 그 매칭은 오래가지 못한다 — 둘 다 기존 매칭을 깨고 새로 짝지어질 동기가 있기 때문이다. NRMP가 막으려던 것이 정확히 이것이었다: 매칭이 발표된 뒤에 “사실 이쪽이 서로 더 낫다“며 뒤집히는 상황.

오늘 배우는 것과의 연결

이 개념은 학문적으로도 인정받아, 게일-섀플리 이론을 발전시킨 로이드 섀플리와 앨빈 로스가 2012년 노벨 경제학상을 받았다.1 오늘은 이 개념을 정확히 정의하고, 주어진 매칭이 stable한지 판정하는 코드를 만든다 — 실제로 매칭을 찾아내는 알고리즘은 다음 주에 다룬다.

70년 전 병원과 의대생 사이의 혼란이, 오늘 배우는 정의 하나로 정확히 설명된다.

Stable Matching II

📓 Jupyter Notebook 열기

2003년 이전, 뉴욕시 고등학교 배정 시스템은 매년 수만 명의 학생을 제대로 배정하지 못한 채 남겼다. 학생들은 여러 학교에 원서를 내고, 학교는 합격자를 발표하고, 학생은 그중 하나를 고르고 — 이 과정을 여러 차례 반복하는 동안 정보가 뒤엉켰고, 정작 빈자리와 갈 곳 없는 학생이 동시에 존재하는 비효율이 반복됐다.

2003년, 경제학자 아트만 압둘카디로글루, 파라그 파탁, 앨빈 로스가 게일-섀플리 알고리즘을 이 시스템에 도입했다.1 결과는 확실했다 — 배정받지 못한 학생 수가 크게 줄었고, 이 방식은 이후 보스턴 등 다른 도시의 학교 배정 시스템에도 그대로 채택됐다.

오늘 배우는 알고리즘이 실제로 하는 일

핵심 아이디어는 단순하다: 자유로운 쪽(예: 남자, 또는 학생)이 자기 선호 순서대로 계속 지원하고, 받는 쪽(예: 여자, 또는 학교)은 지금까지 받은 것 중 최선을 잠정적으로 붙잡아두되, 더 나은 지원이 오면 그쪽으로 바꾼다. 이 과정이 끝나면 항상 — 예외 없이 — stable matching이 만들어진다는 것이 게일과 섀플리가 증명한 정리다.

이번 주는 지난주에 정의한 stable matching을 실제로 찾아내는 propose-reject 알고리즘을 코드로 구현한다. 뉴욕시가 실제로 도입한 것과 원리적으로 동일한 절차다.

Poker Hands

📓 Jupyter Notebook 열기

1946년, 수학자 스타니스와프 울람은 병을 앓고 회복하는 동안 혼자 카드놀이(솔리테어)를 하며 시간을 보내고 있었다. 문득 “이 카드 배치가 나올 확률이 정확히 얼마일까“라는 생각이 들었는데, 조합론으로 정확히 계산하려니 너무 복잡했다. 대신 그는 이렇게 생각했다 — “그냥 카드를 수백 번 실제로 섞어보고, 몇 번이나 그 배치가 나오는지 세어보면 되지 않을까?”

울람은 이 아이디어를 동료 존 폰 노이만에게 전했고, 둘은 이것을 맨해튼 프로젝트의 핵무기 설계 계산(중성자가 물질을 통과하는 과정을 예측하는 문제)에 그대로 적용했다. 정확한 확률을 계산하기엔 너무 복잡한 문제를 무작위 시행을 대량으로 반복해서 근사하는 이 방법에는 이름이 필요했다 — 동료 니콜라스 메트로폴리스는 울람의 삼촌이 즐겨 찾던 모나코의 도박 도시 이름을 따서 몬테카를로(Monte Carlo) 방법 이라고 불렀다.1

카드 게임에서 시작해 카드 게임으로

포커 핸드의 정확한 확률은 조합론으로 계산할 수 있지만(예: straight flush는 정확히 40/2,598,960), 카드 수가 늘어나거나 규칙이 복잡해지면 손으로 계산하기 매우 어려워진다. 이번 주 마지막에 다루는 Monte Carlo 시뮬레이션은 울람이 처음 떠올렸던 바로 그 방식이다 — 무작위 핸드를 대량으로 만들어보고, 각 족보가 몇 번 등장하는지 세어서 확률을 추정한다.

오늘 배우는 것과의 연결

핵무기 설계라는 매우 진지한 문제에 쓰인 방법의 뿌리가 혼자 하는 카드놀이였다는 사실은, 좋은 아이디어가 어디서 시작될 수 있는지를 보여준다.

1973년, 수학자 빅터 클리는 동료 바츨라프 흐바탈에게 이런 질문을 던졌다: “n개의 벽으로 이루어진 미술관을 감시 카메라(또는 경비원)로 전부 감시하려면, 최소 몇 대가 필요한가?” 미술관의 벽이 복잡하게 꺾여 있을수록 사각지대가 늘어난다는 게 직관이었지만, 정확히 몇 대면 충분한지는 아무도 몰랐다.

흐바탈은 곧 답을 내놨다: 어떤 모양의 미술관이든 \(\lfloor n/3 \rfloor\)대면 항상 충분하다(그리고 빗 모양처럼 뾰족한 미술관에서는 그만큼이 실제로 필요하기도 하다).1 몇 년 뒤 스티브 피스크는 이 결과를 훨씬 우아한 방법으로 다시 증명했다 — 미술관을 삼각형들로 쪼갠 뒤, 그 삼각형들의 꼭짓점을 세 가지 색으로 칠할 수 있음을 보이고, 가장 적게 쓰인 색의 꼭짓점에만 카메라를 두면 된다는 것이었다. 2

이번 주 문제와의 관계

이번 주 다루는 문제는 이 유명한 정리의 한 갈래다 — 다만 임의의 다각형이 아니라 rectilinear polygon(모든 벽이 수직/수평)으로 제한하고, 카메라도 딱 1대만 쓴다는 조건을 붙인 특수한 경우다. 조건을 좁힌 대신, “카메라 1대로 전부 감시 가능한 위치가 어디인지“를 정확히 계산해내는 것이 이번 주의 목표다.

How Numbers Live in Memory

이 페이지는 특정 주차에 종속된 내용이 아니라 참고 자료다 — 타입/dtype 관련 질문이 나올 때마다 다시 찾아보면 된다. Week 2에서 언급됐지만 끝까지 파고들지 않았던 질문에 비트 단위로 답한다: 왜 0.1 + 0.2 == 0.3은 False인가?

정수(Integer)

컴퓨터는 모든 것을 비트(0과 1)로 저장한다. n비트 unsigned(부호 없는) 정수는 단순한 이진 자릿값이다 — i번째 비트가 1이면 2^i만큼을 더한다:

비트 00000 101
자릿값 1286432168 421

색칠된(1인) 비트만 값에 기여한다 — 나머지는 전부 0을 더하는 것과 같다: 4 + 1 = 5.

n비트로는 2^n개의 서로 다른 값을 표현할 수 있으므로, unsigned n비트 정수의 범위는 [0, 2^n - 1]이다. n=8이면 [0, 255](예: 이미지의 각 RGB 채널이 쓰는 uint8).

Signed(부호 있는) 정수는 음수도 표현해야 하는데, 거의 모든 언어가 2의 보수(two’s complement) 방식을 쓴다: 어떤 수를 음수로 만들려면 모든 비트를 뒤집고 1을 더한다.

 5  =  00000101
-5  =  11111011      (00000101을 뒤집으면 11111010, 여기에 +1)

맨 앞 비트는 이제 +2^(n-1)이 아니라 -2^(n-1)을 의미하게 되어, 전체 범위가 [-2^(n-1), 2^(n-1) - 1]로 바뀐다 — int8이면 [-128, 127]. 범위가 대칭이 아님(음수가 양수보다 하나 더 많음)에 주목 — 이건 2의 보수 방식의 직접적인 결과이고, 실제 8비트 int8 타입에서 abs(-128)이 오버플로우를 일으키는 이유이기도 하다.

2의 보수가 임의로 정해진 방식은 아니다 — 핵심은 덧셈 회로 하나로 양수든 음수든 완전히 똑같이 처리할 수 있다는 것(뺄셈을 위한 별도 회로가 필요 없음)이다. 그래서 교과서적 관례가 아니라 실제 하드웨어에서 보편적으로 쓰인다.

타입비트 수범위
int8 / uint88[-128, 127] / [0, 255]
int16 / uint1616[-32768, 32767] / [0, 65535]
int32 / uint3232[-2.1×10⁹, 2.1×10⁹] / [0, 4.3×10⁹]
int64 / uint6464[-9.2×10¹⁸, 9.2×10¹⁸] / [0, 1.8×10¹⁹]

Python의 기본 int는 이런 걸 신경 쓸 필요가 없다 — 필요하면 자동으로 자릿수가 무한히 커진다. 대신 같은 값이라도 고정폭 정수보다 느리고 메모리를 더 쓴다. 반대로 numpy/pandas의 배열은 (아래에서 다루듯) 그 오버헤드를 피하려고 일부러 고정폭 타입을 쓴다.

IEEE 754: 부동소수점(Floating-Point) 숫자

float는 “소수점 아래 자릿수“를 그대로 저장하는 게 아니라, 이진수로 된 과학적 표기법처럼 부호 비트 \(s\), 지수 비트 \(e_1e_2\ldots e_k\), 가수 비트 \(m_1m_2\ldots m_n\) 세 부분으로 저장된다.

\[\text{value} = (-1)^s \times \left(1 + 0.m_1m_2\ldots m_n\right)_2 \times 2^{(e_1e_2\ldots e_k)_2 - b}\]

\(m_1 m_2 \ldots m_n\)은 실제 저장된 가수 비트 그 자체를, 소수점 아래 이진 분수(\(0.m_1m_2\ldots\))로 읽은 것이다 — 맨 앞의 1 +는 저장되지 않고, 정규화된(normal) 숫자라면 항상 공짜로 붙는다. 마찬가지로 \((e_1e_2\ldots e_k)_2\)는 지수 비트 그 자체를 부호 없는 이진수로 읽은 값이다 — 이 값을 앞으로 E라고 줄여 쓰자.

타입부호 비트지수 비트(k)가수 비트(n)전체 비트
float16 (half)151016
float32 (single)182332
float64 (double)1115264

bias는 위의 비트 수들과는 성격이 다르다 — bias는 “폭“이 아니라, 실제 지수에 더해서 저장하는 값이다. 이렇게 하면 (부호 비트가 따로 없는) unsigned 지수 필드로도 음수인 실제 지수를 표현할 수 있다:

\[E = \text{실제 지수} + b \quad\Longleftrightarrow\quad \text{실제 지수} = E - b, \qquad b = 2^{k-1} - 1\]

왜 하필 이 값인가? k비트로 표현 가능한 E값은 0부터 \(2^k-1\)까지인데, 그중 양 끝값(E=0과 E=\(2^k-1\))은 일반적인 숫자가 아니라 특수값(0/denormal, 무한대/NaN)을 위해 따로 빼둔다. 실제 지수가 음의 방향으로도 양의 방향만큼 뻗어나갈 수 있도록(그래야 아주 큰 수와 아주 작은 수를 똑같이 잘 표현할 수 있음) b는 그 전체 범위의 대략 절반(2^(k-1))에서, 특수값 쪽으로 하나를 맞추기 위해 1을 뺀 값으로 정한다. float32(k=8)라면 b = 2^7-1 = 127이 되어, 일반적인 숫자의 실제 지수는 대략 -128부터 +127까지 — 0을 기준으로 거의 대칭이 된다.

타입k(지수 비트)b(bias)
float165\(2^4-1=15\)
float328\(2^7-1=127\)
float6411\(2^{10}-1=1023\)

예: float32에서 E=130이면 실제 지수는 130-127=3이다.

특수값들은 정해진 E 패턴으로 인코딩된다: E=0이면 0 또는 denormal(그 공짜 1 +를 가질 만큼 크지 않은 아주 작은 수), E=\(2^k-1\)(지수 비트가 전부 1)이면 ±무한대(가수가 0인 경우) 또는 NaN(가수가 0이 아닌 경우 — 0/0이나 math.sqrt(-1)이 이걸 돌려준다).

왜 0.1 + 0.2 != 0.3인가

십진수 0.1은 1/10인데, 10 = 2×5라서 이진수로 쓰면 무한히 반복되는 소수가 된다 — 마치 1/3이 십진수로 무한히 반복되는 것과 같은 이유다. 가수의 비트 수는 한정되어 있으므로 어딘가에서 잘리고, 실제로 저장되는 값은 0.1이 아니라 그에 가장 가까운 표현 가능한 값이다:

from decimal import Decimal
print(Decimal(0.1))
# 0.1000000000000000055511151231257827021181583404541015625

실제 비트(float64, 가수 52비트):

부호: 0
지수: 01111111011   (1019, 실제 지수 = 1019 - 1023 = -4)
가수: 1001100110011001100110011001100110011001100110011010

0.1과 0.2는 각각 진짜 값에서 아주 조금씩 어긋난 값으로 반올림되는데, 더할 때 그 어긋남이 서로 상쇄되지 않아서 합도 0.3에서 조금 어긋난다. IEEE 754 float를 쓰는 언어라면 전부 이런 현상이 생긴다(Python만의 버그가 아님) — 해결책은 항상 float를 ==로 비교하지 않고 오차범위를 두는 것: abs(a - b) < 1e-9.

32비트 vs 64비트

“32비트”/“64비트“는 CPU 레지스터와 주소의 폭을 가리키는데, 이게 결국 프로그램이 접근할 수 있는 메모리 총량의 한계를 정한다 — 32비트는 정확히 4GB(2^32바이트), 64비트는 약 16EB(2^64바이트, 실제 어떤 컴퓨터도 그만큼의 메모리는 없음)까지. 이는 위에서 다룬 int8/int32/int64 같은 값의 폭과는 별개의 축이다 — 64비트 기계에서도 8비트 값으로 계산할 수 있다.

왜 중요한가: numpy, pandas, 그리고 모델 양자화(Quantization)

평범한 Python int/float는 이런 걸 신경 쓸 필요가 없게 숨겨주지만, numpy나 pandas, 딥러닝 프레임워크를 다루는 순간 선택하는 dtype이 메모리와 속도를 직접 결정한다 — 이제 진짜 고정폭 표현을 고르는 것이기 때문이다:

import numpy as np
np.array([1, 2, 3], dtype=np.int8)     # 원소당 1바이트
np.array([1, 2, 3], dtype=np.int64)    # 원소당 8바이트 — 8배의 메모리
np.array([1.0], dtype=np.float32)      # GPU가 가장 빠르게 계산하는 타입

pandas의 DataFrame 컬럼이 int8/float32로도 충분한 데이터를 int64/float64로 기본 저장해버리는 것은 실제 데이터 파이프라인에서 가장 흔하면서도 피할 수 있는 메모리 낭비 중 하나다 — 나이(0-120) 컬럼이라면 int8이 기본값 int64의 1/8 메모리만 쓰면서도 정보 손실은 전혀 없다.

같은 트레이드오프가 훨씬 큰 규모로 나타나는 것이 바로 머신러닝의 모델 양자화(quantization)다. 거대 언어모델의 가중치(weight)는 원래 float16이나 float32로 학습된다. 예를 들어 OpenAI가 공개한 실제 모델 gpt-oss-20b (약 210억 파라미터, 그중 실제로 쓰이는 것은 매 토큰마다 약 36억)를 16비트로 그대로 저장하면 가중치만으로 약 40GB가 필요하지만, 공식 배포판은 처음부터 4비트대(MXFP4)로 양자화되어 있어 약 12.8GB에 불과하다 — 정확히 위 표에서 본 “비트 수를 줄이면 메모리도 그만큼 준다“는 원리 그대로다. 이렇게 용량을 줄이는 게 바로 데이터센터급 서버가 아니라 일반 GPU 한 장으로도 그 정도 크기의 모델을 돌릴 수 있게 해주는 이유다. 트레이드오프는 실재한다 — 비트 수가 줄면 가중치 하나하나의 정밀도도 줄어들어서, 양자화된 모델은 원본 float16 모델보다 정확도가 약간 떨어진다 — 위에서 본 0.1+0.2 이야기의 “어긋난 그 조금“과 정확히 같은 현상인데, 여기서는 모델이 메모리에 아예 들어갈 수 있게 하려고 의도적으로 감수하는 것이다.

VRAM & Performance Calculator의 실제 화면. 왼쪽에서 모델·양자화 방식(FP32, FP16, Q8, Q4 등)·GPU를 고르면, 오른쪽에서 실제로 필요한 VRAM과 예상 속도를 계산해준다 — 위에서 설명한 “비트 수를 줄이면 메모리도 준다“는 원리를 직접 눌러가며 확인할 수 있다.

위에 나온 모든 dtype 표(int8 vs int64, float16 vs float32)는 결국 지금 막 배운 것과 똑같은 아이디어를, 매번 다른 트레이드오프에 맞춰 고른 것일 뿐이다.
