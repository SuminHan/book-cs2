## 프로그래밍은 왜 여전히 중요한가

*Computer Science 2*

### 1. The Question

"이제 AI가 코드를 짜준다. 나보다 빠르고, 솔직히 나보다 더 잘 짠다. 그런데 내가 왜
프로그래밍 수업에 앉아 있어야 하지?"

정당한 질문이다. 그리고 "AI는 코딩을 잘 못한다"는 식으로 답할 생각은 없다.
**못하지 않는다. 아주 잘하고, 매달 더 좋아지고 있다.** 대신 다른 방식으로
답하려 한다 — 그래서 어떤 일이 새로 생겼는지 보여주는 방식으로.

### 2. What Changed

이진 탐색을 짜달라고 하면 즉시 나온다. 그리고 맞다. 10년 전엔 한 주치 수업
분량이었다. 지금은 4초. 그럼 무엇이 비싸졌는가?

**병목이 옮겨갔다.**

| | 예전 | 지금 |
|---|---|---|
| 어려운 부분 | 코드를 **쓰는** 것 | 코드를 **판단하는** 것 |
| | 하루 100줄을 썼고, 그 100줄을 전부 이해하고 있었음 — 쓰려면 이해할 수밖에 없으니까 | 1분이면 1000줄을 뽑음. 그중 몇 줄이나 이해하고 있나? |

AI가 좋아진다고 이 일이 줄지 않는다. 오히려 늘어난다.

이건 이미 취업 시장에서 나타나고 있다: 신입과 인턴은 취업하기 더 어려워졌고,
빅테크의 평균 연차는 계속 올라가는 중이다 — 그런데 동시에 상위 테크 기업 채용은
1년 전보다 약 20% 증가했고, AI 엔지니어링 공고는 Apple, Google 등에서 50~100%
증가했다.[^job-market] 둘 다 동시에 참이다. 왜? 예전에 입문하는 방법은 "작고
명확하게 정의된 과제를 줄 테니 구현해와라"였다. 그건 지금 AI가 가장 잘하는
일이다. 그 첫 계단이 사라졌다. 남은 일은 한 단계 위에서 시작한다 — 결정하고,
지시하고, 검증하는 일.

[^job-market]: The Pragmatic Engineer, [*State of the Software Engineering
    Job Market 2026*](https://newsletter.pragmaticengineer.com/p/state-of-the-job-market-2026)
    and [*The Job Market in 2026, Part 2*](http://newsletter.pragmaticengineer.com/p/the-job-market-in-2026-part-2).

들어갈 때는 한국어든 영어든 사람의 언어를 쓸 수 있다. 하지만 돌아올 때는 답이
항상 코드다 — 출력에는 한국어 버전이 없다. 오직 코드가 있을 뿐이고, 그걸 읽을 수
있느냐만 남는다. **돌아온 것을 읽지 못한다면, 지시를 한 게 아니라 소원을 빈
것이다.**

### 3. The Gap

"성적 계산기를 만들어줘"라고 시켜봤다. 이렇게 나왔다 — 깔끔하고, 읽기 쉽고, 잘
돌아간다:

```python
def final_grade(scores, attendance_rate):
    average = sum(scores) / len(scores)
    if attendance_rate < 0.75:
        return "Fail"
    return "Pass" if average >= 70 else "Fail"
```

맞아 보인다. 돌아간다. 에러도 없다. 그런데 이 수업 기준으로는 틀렸다.

**중요한 건 이 부분이다: 어디를 봐도 틀려 보이지 않는다는 것. 경고해주지
않는다. 그냥 조용히 잘못된 성적을 계산할 뿐이다.**

세 가지를 알 수 없었다:

- 어떤 학생이 병결로 시험을 못 봤다. 우리 규정은 인정점수에 80% 가중치를 —
  공결이면 100%를 적용한다. 코드에는 둘 다 없다.
- 어떤 학생이 Fail을 받고 재시험을 봤다. 어느 점수를 쓰는가? 코드는 재시험이란 걸
  들어본 적이 없다.
- 출석 3/4 미만 — 이게 모든 걸 덮어쓰는가, 아니면 먼저 확인하는가? 코드는
  찍었다. 그리고 우리와 다르게 찍었다.

"그럼 규정을 프롬프트에 넣으면 되잖아요!" — 맞다. 그런데 그렇게 하려면 뭐가
빠졌는지를 이미 알아챘어야 한다. 코드는 알려주지 않았다. **구멍을 보려면
읽는 수밖에 없었다.**

### 4. The Trap

**과제:** 어떤 연도가 윤년이면 `True`를 반환.

```python
def is_leap_year(year):
    if year % 4 == 0:
        return True
    else:
        return False
```

테스트해봤다: `is_leap_year(2024)` → `True`, 정답! 통과했다. 이대로 제출?

`is_leap_year(1900)`을 테스트해보면 — 기대값은 `False`(1900년은 윤년이 아니었다)인데
실행 결과는 `True`. 왜: 진짜 규칙은 세 부분이다 — 4로 나누어떨어지고, 단 100으로
나누어떨어지면 제외하되, 그중 400으로 나누어떨어지면 다시 윤년. 코드는 첫 부분만
알고 있다. 1900은 100으로는 나뉘지만 400으로는 안 나뉘므로 윤년이 아니다.

버그는 처음부터 거기 있었다. 테스트가 그쪽을 안 봤을 뿐이다. **테스트를
통과했다는 건 맞다는 뜻이 아니다.** 어떤 입력이 이걸 깨뜨리는지 고르는 것 —
그게 실력이다. 그리고 그건 아무도 대신 해줄 수 없다.

같은 패턴이 실제로도 있었다: NASA의 Mars Climate Orbiter는 10개월을 날아갔고,
화성 상공 약 150km에 안착할 예정이었으나 실제로는 57km로 진입해 대기권
한복판에서 부서졌다 — 한 팀은 추력 값을 파운드힘(lbf) 단위로 넘겼고, 받는 팀은
그걸 뉴턴(N)으로 읽었다. 1 lbf = 4.45 N이라 모든 궤도 수정이 4.45배씩 어긋난 채로
10개월이 지났다. 손실 1억 2500만 달러. **그 코드는 한 줄도 빠짐없이 완벽하게
돌아갔다. 그 숫자가 무슨 뜻인지 아무도 확인하지 않았을 뿐이다.**

### 5. Your Job

1950년 튜링은 "기계가 생각할 수 있는가?"라고 물었고 — 답하기를 거부했다. 대신
시험으로 바꿨다: 사람 심판이 양쪽에 질문을 던지고 그 답이 말이 되는지 판단한다.
컴퓨터의 맨 처음 설계에 이미 질문을 던지는 사람이 의자에 앉아 있었다. 그 의자는
끝내 자동화되지 않았다.

이 과목의 교과 핵심역량 네 가지 — 그리고 방금 각각을 어디서 만났는지:

- **Fundamental Programming & Problem-Solving** — 돌아온 코드를 읽고, 그게
  실제로 무슨 일을 하는지 이해하기
- **Logical Thinking & Analytical Skills** — 어떤 입력이 이걸 깨뜨릴지, 깨지기
  전에 알기
- **Communication & Collaboration** — 수업 시간에 문제를 같이, 소리 내어 푸는 이유
- **Ethical Use of AI & Responsible Attitude** — 도구는 쓰되, 답에 대한 책임은
  내가 진다. "AI가 짰는데요"는 변명이 되지 않는다.

기계보다 코드를 빨리 치려고 여기 온 게 아니다. 원하는 것을 정확히 말할 수 있고,
돌아온 것을 읽을 수 있고, 어떤 입력이 깨뜨릴지 아는 사람이 되기 위해서다. 그래서
수업은 이렇게 운영된다: 수업 시간에 문제는 AI 없이, 다 같이, 손으로 푸는 게
원칙이다. AI를 쓰는 게 부정행위라서가 아니라 — 기계가 대신 해주는 능력은 내
것이 되지 않기 때문이다.

평생 계산기를 쓸 것이다. 그래도 산수는 손으로 배웠다.
