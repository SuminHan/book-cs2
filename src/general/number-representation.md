## 정수(Integer)

컴퓨터는 모든 것을 비트(0과 1)로 저장한다. `n`비트 **unsigned**(부호 없는)
정수는 단순한 이진 자릿값이다 — `i`번째 비트가 1이면 `2^i`만큼을 더한다:

<td style="color:#888">0</td><td style="color:#888">0</td><td style="color:#888">0</td><td style="color:#888">0</td><td style="color:#888">0</td>
<td style="color:#d6336c"><b>1</b></td><td style="color:#888">0</td><td style="color:#d6336c"><b>1</b></td></tr>
<tr><td>자릿값</td>
<td style="color:#888">128</td><td style="color:#888">64</td><td style="color:#888">32</td><td style="color:#888">16</td><td style="color:#888">8</td>
<td style="color:#d6336c"><b>4</b></td><td style="color:#888">2</td><td style="color:#d6336c"><b>1</b></td></tr>
</table>

색칠된(`1`인) 비트만 값에 기여한다 — 나머지는 전부 `0`을 더하는 것과 같다:
`4 + 1 = 5`.

`n`비트로는 `2^n`개의 서로 다른 값을 표현할 수 있으므로, unsigned `n`비트
정수의 범위는 `[0, 2^n - 1]`이다. `n=8`이면 `[0, 255]`(예: 이미지의 각
RGB 채널이 쓰는 `uint8`).

**Signed**(부호 있는) 정수는 음수도 표현해야 하는데, 거의 모든 언어가
**2의 보수(two's complement)** 방식을 쓴다: 어떤 수를 음수로 만들려면
모든 비트를 뒤집고 1을 더한다.

```
 5  =  00000101
-5  =  11111011      (00000101을 뒤집으면 11111010, 여기에 +1)
```

맨 앞 비트는 이제 `+2^(n-1)`이 아니라 `-2^(n-1)`을 의미하게 되어, 전체
범위가 `[-2^(n-1), 2^(n-1) - 1]`로 바뀐다 — `int8`이면 `[-128, 127]`.
범위가 대칭이 아님(음수가 양수보다 하나 더 많음)에 주목 — 이건 2의 보수
방식의 직접적인 결과이고, 실제 8비트 `int8` 타입에서 `abs(-128)`이
오버플로우를 일으키는 이유이기도 하다.

2의 보수가 임의로 정해진 방식은 아니다 — 핵심은 덧셈 회로 하나로 양수든
음수든 완전히 똑같이 처리할 수 있다는 것(뺄셈을 위한 별도 회로가 필요
없음)이다. 그래서 교과서적 관례가 아니라 실제 하드웨어에서 보편적으로
쓰인다.

| 타입 | 비트 수 | 범위 |
|---|---|---|
| `int8` / `uint8` | 8 | `[-128, 127]` / `[0, 255]` |
| `int16` / `uint16` | 16 | `[-32768, 32767]` / `[0, 65535]` |
| `int32` / `uint32` | 32 | `[-2.1×10⁹, 2.1×10⁹]` / `[0, 4.3×10⁹]` |
| `int64` / `uint64` | 64 | `[-9.2×10¹⁸, 9.2×10¹⁸]` / `[0, 1.8×10¹⁹]` |

Python의 기본 `int`는 이런 걸 신경 쓸 필요가 없다 — 필요하면 자동으로
자릿수가 무한히 커진다. 대신 같은 값이라도 고정폭 정수보다 느리고 메모리를
더 쓴다. 반대로 `numpy`/`pandas`의 배열은 (아래에서 다루듯) 그 오버헤드를
피하려고 일부러 고정폭 타입을 쓴다.

## IEEE 754: 부동소수점(Floating-Point) 숫자

float는 "소수점 아래 자릿수"를 그대로 저장하는 게 아니라, 이진수로 된
과학적 표기법처럼 **부호 비트 `s`, 지수 비트 `e_1e_2...e_k`, 가수 비트
`m_1m_2...m_n`** 세 부분으로 저장된다.

\\[\text{value} = (-1)^s \times \left(1 + 0.m_1m_2\ldots
m_n\right)_2 \times 2^{(e_1e_2\ldots e_k)_2 - b}\\]

`m_1 m_2 ... m_n`은 실제 저장된 가수 비트 그 자체를, 소수점 아래 이진
분수(`0.m_1m_2...`)로 읽은 것이다 — 맨 앞의 `1 +`는 저장되지 않고,
정규화된(normal) 숫자라면 항상 공짜로 붙는다. 마찬가지로
`(e_1e_2...e_k)_2`는 지수 비트 그 자체를 부호 없는 이진수로 읽은
값이다 — 이 값을 앞으로 `E`라고 줄여 쓰자.

| 타입 | 부호 비트 | 지수 비트(`k`) | 가수 비트(`n`) | 전체 비트 |
|---|---|---|---|---|
| `float16` (half) | 1 | 5 | 10 | 16 |
| `float32` (single) | 1 | 8 | 23 | 32 |
| `float64` (double) | 1 | 11 | 52 | 64 |

**bias는 위의 비트 수들과는 성격이 다르다** — bias는 "폭"이 아니라, 실제
지수에 더해서 저장하는 **값**이다. 이렇게 하면 (부호 비트가 따로 없는)
unsigned 지수 필드로도 음수인 실제 지수를 표현할 수 있다:

\\[E = \text{실제 지수} + b \quad\Longleftrightarrow\quad
\text{실제 지수} = E - b, \qquad b = 2^{k-1} - 1\\]

**왜 하필 이 값인가?** `k`비트로 표현 가능한 `E`값은 `0`부터
\\(2^k-1\\)까지인데, 그중 양 끝값(`E=0`과 `E=`\\(2^k-1\\))은 일반적인
숫자가 아니라 특수값(0/denormal, 무한대/NaN)을 위해 따로 빼둔다.
**실제 지수가 음의 방향으로도 양의 방향만큼 뻗어나갈 수 있도록**(그래야
아주 큰 수와 아주 작은 수를 똑같이 잘 표현할 수 있음) `b`는 그 전체
범위의 대략 절반(`2^(k-1)`)에서, 특수값 쪽으로 하나를 맞추기 위해 `1`을
뺀 값으로 정한다. `float32`(`k=8`)라면 `b = 2^7-1 = 127`이 되어,
일반적인 숫자의 실제 지수는 대략 `-128`부터 `+127`까지 — `0`을 기준으로
거의 대칭이 된다.

| 타입 | `k`(지수 비트) | `b`(bias) |
|---|---|---|
| `float16` | 5 | \\(2^4-1=15\\) |
| `float32` | 8 | \\(2^7-1=127\\) |
| `float64` | 11 | \\(2^{10}-1=1023\\) |

예: `float32`에서 `E=130`이면 실제 지수는 `130-127=3`이다.

**특수값**들은 정해진 `E` 패턴으로 인코딩된다: `E=0`이면 `0` 또는
*denormal*(그 공짜 `1 +`를 가질 만큼 크지 않은 아주 작은 수),
`E=`\\(2^k-1\\)(지수 비트가 전부 1)이면 `±무한대`(가수가 0인 경우)
또는 `NaN`(가수가 0이 아닌 경우 — `0/0`이나 `math.sqrt(-1)`이 이걸
돌려준다).

## 왜 `0.1 + 0.2 != 0.3`인가

십진수 `0.1`은 `1/10`인데, `10 = 2×5`라서 **이진수**로 쓰면 무한히
반복되는 소수가 된다 — 마치 `1/3`이 십진수로 무한히 반복되는 것과 같은
이유다. 가수의 비트 수는 한정되어 있으므로 어딘가에서 잘리고, 실제로
저장되는 값은 `0.1`이 아니라 그에 가장 가까운 표현 가능한 값이다:

```python
from decimal import Decimal
print(Decimal(0.1))
# 0.1000000000000000055511151231257827021181583404541015625
```

실제 비트(`float64`, 가수 52비트):

```
부호: 0
지수: 01111111011   (1019, 실제 지수 = 1019 - 1023 = -4)
가수: 1001100110011001100110011001100110011001100110011010
```

`0.1`과 `0.2`는 각각 진짜 값에서 아주 조금씩 어긋난 값으로 반올림되는데,
더할 때 그 어긋남이 서로 상쇄되지 않아서 합도 `0.3`에서 조금 어긋난다.
IEEE 754 float를 쓰는 언어라면 전부 이런 현상이 생긴다(Python만의
버그가 아님) — 해결책은 항상 float를 `==`로 비교하지 않고 오차범위를 두는
것: `abs(a - b) < 1e-9`.

## 32비트 vs 64비트

"32비트"/"64비트"는 CPU 레지스터와 주소의 폭을 가리키는데, 이게 결국
프로그램이 접근할 수 있는 메모리 총량의 한계를 정한다 — 32비트는 정확히
4GB(`2^32`바이트), 64비트는 약 16EB(`2^64`바이트, 실제 어떤 컴퓨터도
그만큼의 메모리는 없음)까지. 이는 위에서 다룬 int8/int32/int64 같은
*값*의 폭과는 별개의 축이다 — 64비트 *기계*에서도 8비트 *값*으로 계산할
수 있다.

## 왜 중요한가: `numpy`, `pandas`, 그리고 모델 양자화(Quantization)

평범한 Python `int`/`float`는 이런 걸 신경 쓸 필요가 없게 숨겨주지만,
`numpy`나 `pandas`, 딥러닝 프레임워크를 다루는 순간 선택하는 dtype이
메모리와 속도를 직접 결정한다 — 이제 진짜 고정폭 표현을 고르는 것이기
때문이다:

```python
import numpy as np
np.array([1, 2, 3], dtype=np.int8)     # 원소당 1바이트
np.array([1, 2, 3], dtype=np.int64)    # 원소당 8바이트 — 8배의 메모리
np.array([1.0], dtype=np.float32)      # GPU가 가장 빠르게 계산하는 타입
```

`pandas`의 `DataFrame` 컬럼이 `int8`/`float32`로도 충분한 데이터를
`int64`/`float64`로 기본 저장해버리는 것은 실제 데이터 파이프라인에서
가장 흔하면서도 피할 수 있는 메모리 낭비 중 하나다 — 나이(0-120) 컬럼이라면
`int8`이 기본값 `int64`의 1/8 메모리만 쓰면서도 정보 손실은 전혀 없다.

같은 트레이드오프가 훨씬 큰 규모로 나타나는 것이 바로 머신러닝의 **모델 양자화**(quantization)다.
거대 언어모델의 가중치(weight)는 원래 `float16`이나 `float32`로 학습된다.
예를 들어 OpenAI가 공개한 실제 모델 [gpt-oss-20b](https://huggingface.co/openai/gpt-oss-20b)
(약 210억 파라미터, 그중 실제로 쓰이는 것은 매 토큰마다 약 36억)를
16비트로 그대로 저장하면 가중치만으로 약 40GB가 필요하지만, 공식
배포판은 처음부터 4비트대(`MXFP4`)로 양자화되어 있어 약 12.8GB에
불과하다 — 정확히 위 표에서 본 "비트 수를 줄이면 메모리도 그만큼 준다"는
원리 그대로다. 이렇게 용량을 줄이는 게 바로 데이터센터급 서버가 아니라
일반 GPU 한 장으로도 그 정도 크기의 모델을 돌릴 수 있게 해주는 이유다.
트레이드오프는 실재한다 — 비트 수가 줄면 가중치 하나하나의 정밀도도
줄어들어서, 양자화된 모델은 원본 `float16` 모델보다 정확도가 약간
떨어진다 — 위에서 본 `0.1+0.2` 이야기의 "어긋난 그 조금"과 정확히 같은
현상인데, 여기서는 모델이 메모리에 아예 들어갈 수 있게 하려고 의도적으로
감수하는 것이다. (이런 정확도 하락을 실제로 측정할 때는
[EleutherAI의 lm-evaluation-harness](https://github.com/EleutherAI/lm-evaluation-harness)
(Hugging Face의 [Open LLM
Leaderboard](https://huggingface.co/spaces/open-llm-leaderboard/open_llm_leaderboard)가
바로 이걸 기반으로 함)나, 하드웨어/추론 성능까지 표준화해서 비교하는
[MLPerf](https://mlcommons.org/benchmarks/inference-datacenter/) 같은
벤치마크를 쓰고, 특정 모델·양자화·GPU 조합에 실제로 VRAM이 얼마나
필요하고 속도가 얼마나 나올지는 [ApX Machine Learning의 VRAM &
Performance Calculator](https://apxml.com/tools/vram-calculator) 같은
도구로 직접 계산해볼 수 있다.)
